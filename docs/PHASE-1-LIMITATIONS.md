# Phase 1 limitations and security notes

This proof is for local development with untrusted C contained by Wasm imports and browser Workers, but it is **not a production security boundary**. It follows the [Phase 0 threat model](SECURITY-MODEL.md); the hardened separate-origin iframe and CSP have not been built or tested.

| Area | Implemented and verified | Limit or open risk |
| --- | --- | --- |
| Isolation | Compiler and user Wasm execute in separate Workers; execution Worker is new per run and terminable. Guest Wasm imports observed from `wasi_snapshot_preview1` only. | Worker JavaScript shares the page origin and can use `fetch`; a compiler/runtime compromise may reach same-origin data. No isolated-origin frame, CSP or parent-origin message gate yet. Workers alone are not a complete sandbox. |
| Filesystem/network | No execution directory preopen. A tested absolute-path `fopen` failed. No sockets are supplied to WASI; import gate rejects `sock_*` and non-P1 import modules. | Unsupported syscalls may trap or return errors depending on shim/libc behavior; no broad syscall corpus was run. JS glue can still request network resources on the origin. Compiler Worker holds an in-memory project and sysroot, with no OS filesystem. |
| Infinite loops | Facade deadline on the main thread terminates the disposable execution Worker; a 200 ms loop test rejected and a later run passed. | The deadline is best effort under browser scheduling/tab suspension. No instruction/fuel quota or hard CPU cap. Compile deadline is 30 s and initialization deadline 120 s, but their timeout recovery paths were not adversarially tested. |
| Memory | Input caps and output retained-byte caps are implemented. Execution Worker rejects Wasm binaries over 16 MiB. | No hard per-Worker or WebAssembly memory cap. Compiler may allocate far more than source size; browser tab/process may die under memory pressure. Peak memory was not measured. The facade does not reject an oversize compiled artifact until execution Worker admission. |
| Output | fd 1 and fd 2 capture independently, with 128 KiB retained per stream; flood test verified stdout truncation. | Program continues writing after capture fills until it exits or times out. Compiler diagnostic transcript is not yet bounded. Public message/result aggregate size is not capped. |
| Validation | Facade checks request shape, file count/size, path traversal, allowed C17/O0/warning options, stdin size, artifact provenance and busy state. | Direct Worker messages receive only minimal checks. No complete protocol fuzzing, Unicode/path boundary suite, or stale-response injection. `entry` selects an existing `.c` but does not force `main` to reside there. The compiler's fresh in-memory filesystem uses relative paths at its root; the Phase 0 `/project` layout and deterministic source ordering are not yet implemented. |
| Recovery | Timeout retires a Worker, advances generation and invalidates artifacts; a following run passed. Disposal terminates Workers. | Full `cancel()`/`reset()` and recovery state machine from Phase 0 are deferred. Unexpected compiler Worker failure can leave engine `failed` until explicit `initialize()`. No proof across browser crash or tab suspension. |
| Compatibility | Edge 154 on Windows passed 26 checks. | Chrome, Firefox, Safari, mobile browsers, CSP variations and independent consumers have not been tested. Browsercc lower-level exports and `-###` parsing are version-sensitive. The WASI shim explicitly has incomplete coverage in its [upstream repository](https://github.com/bjorn3/browser_wasi_shim). |
| Assets and legal | npm lock pins package versions; required asset bytes and SHA-256 hashes are recorded. | No runtime hash verification, versioned asset bundle, third-party notice inventory or completed binary license audit. The package is private; root license is pending owner selection. |

The preliminary [Phase 0 limits](RESOURCE-LIMITS.md) are design targets. Phase 1 actually enforces 32 files, 128 KiB per source file, 512 KiB aggregate source, 256-byte paths, 128 KiB stdin, 128 KiB retained each for stdout/stderr, 16 MiB direct execution binary, and a 15 s default execution timeout (constructor may lower it). Compilation and initialization use 30 s and 120 s deadlines respectively. A 16-segment path cap, diagnostic cap, combined message cap, compiler response cap, total artifact budget and measured runtime memory budget are **not implemented**. Do not treat proposed Phase 0 numbers as current guarantees.

Before using the engine in a sensitive IDE, the next security work must include a separate-origin iframe or equivalent origin boundary, strict origin/source/schema checks, tested CSP, asset integrity, bounded compiler output, and a multi-browser adverse workload suite. A browser alone cannot promise strict memory or real-time CPU limits.
