# Phase 0 compiler and runtime research

_Research snapshot: 2026-10-03. “Verified” below means confirmed in linked project documentation or source, not tested in this repository. No toolchain was installed in Phase 0._

## Requirements and comparison

The engine needs actual C compilation and linking in a browser, in-browser execution, standard I/O, a bounded virtual filesystem, diagnostics, and an integration surface that an independent IDE can call. A native `wasi-sdk` binary on the developer's computer does not satisfy browser compilation.

### Criteria check for the leading paths

“Clang host” below means the pinned `browsercc` assets plus an engine-owned adapter, **not** a claim that its convenience function already implements all behavior. “SDK” means stock `wasi-sdk` release binaries. “TraceCC” is a separate browser distribution.

| Criterion | Clang host (proposed) | Stock SDK | TraceCC |
| --- | --- | --- | --- |

| Actual C compilation | Yes, Clang C frontend; confirm pinned C17 build | Yes, but on desktop/build host | Explicit C17 |

## WASI and WebAssembly boundary

Choose **WASI Preview 1 (`wasi_snapshot_preview1`, `wasm32-wasip1`)** for the initial output ABI. It is a core Wasm module interface with broad runtime support and preopened file descriptors. Preview 2 is based on the Component Model and WIT, with a different runtime and packaging path; it can be investigated later behind the adapter. Preview 3's async model is also outside initial scope. A browser does **not** automatically implement WASI: JavaScript must supply imports. The `@bjorn3/browser_wasi_shim` project demonstrates browser instantiation and stdin/stdout, but explicitly says its Preview 1 implementation is incomplete. The exact import set needed by the chosen sysroot is a Phase 1 gate. [WASI P1](https://wasi.dev/releases/wasi-p1), [WASI P2](https://wasi.dev/releases/wasi-p2), [browser shim](https://github.com/bjorn3/browser_wasi_shim).

Initial output is a single-threaded `wasm32-wasip1` command with `_start`. Avoid threads, sockets, dynamic loading, and browser APIs. No SharedArrayBuffer or cross-origin isolation is assumed for the baseline. Inspect actual imports and Wasm features before claiming compatibility with any browser. `wasi-libc` covers many standard I/O, string, allocation, time, and file APIs, but individual functions may be limited by the WASI host and preopens. [wasi-libc](https://github.com/WebAssembly/wasi-libc).

## Recommendation

Use **Clang/LLD compiled to Wasm, initially evaluated through a pinned `browsercc` build**, paired with a pinned WASI Preview 1 sysroot and a browser WASI host. Keep the browsercc API private behind a compiler adapter. It meets the core browser-only C workflow in published source, has an approachable JavaScript integration surface, exposes actual compiler/linker stages, and has less immediate licensing friction than TraceCC. A dedicated compiler Worker runs Clang/LLD; a distinct disposable execution Worker instantiates the produced module with only curated WASI imports. [browsercc README](https://github.com/BertalanD/browsercc), [source](https://github.com/BertalanD/browsercc/blob/main/index.ts), [Wasm linker](https://lld.llvm.org/WebAssembly.html).

This is a **provisional toolchain selection, not a release certification**. The existing browsercc convenience `compile()` handles one translation unit; Phase 1 must prove controlled multi-file C compilation using lower-level Clang/LLD or identify a maintained replacement. The engine must not expose arbitrary compiler flags: accept an allowlist (`c17`, warning profile, `O0` initially) and create its own internal paths. Clang's general optimization support does not prove that every level behaves acceptably in this browser build. [Clang options](https://clang.llvm.org/docs/CommandGuide/clang.html).

### Feasibility gates for Phase 1

1. In a real browser Worker, compile `main.c` with `stdio.h` to a `wasm32-wasip1` command, run it with the chosen WASI host, and capture stdout and exit code.
2. Compile two `.c` translation units plus a user header, link once, and run. If the wrapper cannot safely expose this, build an adapter from pinned Clang/LLD exports or switch to a better distribution.
3. Check syntax warning/error locations, link errors, stdin and stderr, nonzero exit, and all actual Wasm imports/features.
4. Terminate an infinite loop's execution Worker and a stalled compiler Worker from the manager; verify subsequent use.
5. Measure cold/warm load, asset bytes, peak memory, and browser coverage; inventory every redistributed license and source obligation.

If gate 1 fails, the compiler/runtime choice is not accepted. If gate 2 fails, initial multi-file release cannot proceed on this adapter. The fallback is a pinned, reproducible browser-hosted Clang/LLD build using `wasi-sdk` sysroot inputs, drawing on [wasm-clang](https://github.com/binji/wasm-clang) or the [CppStudio browser build](https://github.com/cppstudio-io/wasm-clang-runtime) as build references. This retains the public API and WASI P1 result ABI but costs significant build and maintenance effort. TraceCC is a technical alternative only after explicit AGPL distribution review.

## Open questions and licenses

- Pin candidate versions, hashes, and a matching sysroot; confirm whether browsercc's packaged assets are reproducible and C-only assets can be trimmed.
- Confirm linker invocation, multiple sources, diagnostics format, C17 support, warning flags and optimization in the selected browser build.
- Confirm which WASI imports the generated programs use and whether the browser shim's subset is sufficient. Do not promise arbitrary POSIX calls.
- Quantify asset transfer and memory on target browsers; repository size figures are uncompressed upstream claims, not local measurements.
- Review `browsercc` MIT wrapper, LLVM/Clang/LLD Apache-2.0 WITH LLVM-exception, Emscripten glue MIT, wasi-libc's multiple license files, compiler-rt and any packaged third-party material.
